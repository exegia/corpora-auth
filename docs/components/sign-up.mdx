title: "Sign-up blocks"
description: "SignUpForm for a single-screen registration, OnboardingFlow for the whole funnel."
---

Pick one: `SignUpForm` is registration alone, `OnboardingFlow` wraps it in a confirmation wait and your profile steps.

## SignUpForm

Email, password and confirm-password, with the mismatch caught client-side.

<Frame caption="SignUpForm">
  <img src="/images/blocks/sign-up-form.png" alt="SignUpForm: email, password and confirm-password fields with a Create account button" width="420" />
</Frame>

On success it switches to its own "check your inbox" state when the project requires email confirmation, and reports `pendingConfirmation` versus `signedIn` through `onSuccess`.

```tsx
import { SignUpForm } from "@exegia/auth-ui";
import { z } from "zod";

<SignUpForm
  passwordPolicy={z.string().min(12, "Use at least 12 characters")}
  onSuccess={(result) =>
    result.status === "pendingConfirmation"
      ? setScreen("inbox")
      : navigate("/app")
  }
/>;
```

| Prop | Type | Does |
| --- | --- | --- |
| `onSuccess` | `(result: SignUpResult) => void` | `{ status: "signedIn" \| "pendingConfirmation", session? }` |
| `passwordPolicy` | `z.ZodType<string>` | Replaces the default minimum-8 rule |
| `errorMessages` | `ErrorMessageOverrides` | Per-kind copy overrides |
| `className` | `string` | Merged onto the root element |

`passwordPolicy` takes any zod schema, so your server's rules and the form's stay one definition.

Permissions: **default set**.

## OnboardingFlow

The whole sign-up funnel: credentials, then a confirmation waiting state, then your declared profile steps, then one completion signal.

<Frame caption="OnboardingFlow at the credentials step, with step progress above">
  <img src="/images/blocks/onboarding-flow.png" alt="OnboardingFlow: a two-step progress list above the credentials step" width="420" />
</Frame>

```tsx
import { OnboardingFlow } from "@exegia/auth-ui";

<OnboardingFlow
  steps={[
    {
      id: "profile",
      title: "Your profile",
      fields: [
        { kind: "text", name: "display_name", label: "Display name", required: true },
      ],
    },
  ]}
  onSignInInstead={() => setScreen("signIn")}
  onComplete={({ user, profile }) => navigate("/app")}
/>;
```

| Prop | Type | Does |
| --- | --- | --- |
| `steps` | `OnboardingStepConfig[]` | Profile steps after sign-up. Default: one display-name step |
| `onComplete` | `({ user, profile }) => void` | Fires exactly once, after the final write lands |
| `onSignInInstead` | `() => void` | Renders the "already registered?" escape hatch |
| `passwordPolicy` | `z.ZodType<string>` | Forwarded to the credentials step |
| `showCompleteScreen` | `boolean` | Default `true` — a brief success screen before handing back |
| `errorMessages` | `ErrorMessageOverrides` | Per-kind copy overrides |
| `className` | `string` | Merged onto the root element |

Steps are data, not markup: an `id`, a `title`, and typed `fields`.

```ts
interface OnboardingStepConfig {
  id: string; // unique within the flow, stable across releases
  title: string;
  description?: string;
  fields: FieldConfig[];
}

interface FieldConfigBase {
  name: string; // the user_metadata key the value is written to
  label: string;
  required?: boolean; // required fields gate step advance
  placeholder?: string;
  validate?: z.ZodTypeAny; // composed onto the generated base schema
}

type FieldConfig =
  | (FieldConfigBase & { kind: "text" | "textarea" | "url" })
  | (FieldConfigBase & { kind: "checkbox" })
  | (FieldConfigBase & { kind: "select"; options: { value: string; label: string }[] });
```

Progress is persisted in `user_metadata`, so a flow abandoned halfway resumes where it left off on the next launch. That is why it needs `allow-update-user`.

Permissions: `allow-update-user` (opt-in) plus the default set.
