# Phase 0 Research: Supabase Authentication Plugin for Tauri with Auth UI Kit

**Branch**: `001-supabase-auth-plugin` | **Date**: 2026-07-20

All Technical Context unknowns are resolved below. Each entry records the decision, rationale, and alternatives considered.

## R1. Rust auth engine: `supabase-lib-rs`, wrapped behind an internal trait

**Decision**: Use `supabase-lib-rs` **0.5.3** (crates.io, auth + session-management features) as the auth engine, but never expose its types or client directly. All access goes through a plugin-internal `AuthEngine` abstraction (thin wrapper module) so the crate can be replaced without touching commands, events, or the frontend API.

**Rationale**: The feature description names `supabase-lib-rs` explicitly, and its verified API surface covers most of the spec: email/password sign-up/sign-in (`sign_up_with_email_and_password`, `sign_in_with_email_and_password`), magic link (`sign_in_with_magic_link`), OTP verify (`verify_otp`), sign-out, `refresh_session()` + `needs_refresh_with_buffer()`, `current_user()` / `get_session()` / `set_session()`, password reset (`reset_password_for_email`), user update (`update_user`), and auth-state callbacks (`on_auth_state_change`). Models (`Session { access_token, refresh_token, expires_at, user }`, `User { id, email, phone, *_confirmed_at, user_metadata, ... }`) map cleanly to the spec's entities. Its `Error` enum (18 variants incl. `Auth`, `Network`, `Config`, `RateLimit`) maps onto the spec's error categories (FR-011).

**Known risks (verified against source, drive the mitigations in R2–R4)**:
- Dormant: single maintainer, last commit 2025-10-16 (~9 months idle).
- **PKCE is not implemented** despite README claims (zero hits for `pkce`/`code_challenge`/`exchange_code` in `src/`). `sign_in_with_oauth` only builds the `/authorize` URL.
- **Automatic background refresh is a stub** (`src/session/mod.rs` contains a literal `TODO`); only manual `refresh_session()` + expiry helpers exist.
- Heavy mandatory deps (`image`, `qrcode`, `totp-rs`, `phonenumber`) — compile-time cost, acceptable for v1.

**Alternatives considered**:
- `supabase-auth` 0.10.14 (proziam) — most credible dedicated auth crate, better maintained; rejected for v1 because the spec names supabase-lib-rs, and the wrapper trait keeps a later swap cheap.
- `supabase-auth-rs` 0.1.0 (supabase-community) — official org but explicitly beta, one release, negligible adoption.
- Direct GoTrue REST client (~10 endpoints via reqwest) — most control; rejected as the *primary* engine to honor the spec, but adopted *selectively* for the PKCE exchange (R2) where the crate has no coverage.

## R2. Desktop OAuth: in-plugin PKCE against GoTrue REST + localhost loopback callback

**Decision**: Implement the third-party provider round-trip (FR-010) inside the plugin:
1. Build the authorize URL with `flow_type=pkce` + `code_challenge` (S256), generated by the plugin.
2. Open it in the **system browser** (tauri-plugin-opener / `open`).
3. Capture the redirect on an **ephemeral localhost HTTP server** (the `tauri-plugin-oauth` pattern: bind `http://127.0.0.1:{port}`, one-shot, shut down after capture; port range configurable).
4. Exchange the auth code via `POST /auth/v1/token?grant_type=pkce` with the `code_verifier` (small reqwest call — this is the one place we bypass supabase-lib-rs, since it lacks PKCE entirely).
5. Inject the resulting session into the engine via `set_session(...)` so all downstream behavior (refresh, events, persistence) is uniform.

**Rationale**: Loopback redirect is the sanctioned native-app pattern and the most provider-compatible (Google/GitHub reject custom schemes as redirect URIs). PKCE is Supabase's recommendation for public desktop clients; the implicit flow returns tokens in a URL *fragment*, which a localhost server never receives without a JS shim — PKCE avoids that hack and is strictly more secure. Abandoned round-trips (edge case) are handled by a flow timeout + explicit cancel command; the server is one-shot so a stale redirect cannot create a session.

**Alternatives considered**:
- `tauri-plugin-deep-link` custom scheme — kept as a documented future option; unreliable in dev on macOS (requires installed bundle) and rejected by major providers as a redirect target.
- Implicit flow + fragment-forwarding HTML page — works but weaker security posture and more moving parts; rejected.
- Depending on `tauri-plugin-oauth` (FabianLars) as a crate — the server is ~100 lines; vendoring the pattern inside our plugin avoids a third-party runtime dependency and lets us bind the PKCE state to the server lifecycle.

## R3. Automatic session refresh: plugin-owned tokio task

**Decision**: The plugin runs its own background refresh task (tokio, spawned in the plugin `setup` hook): sleep until `expires_at − buffer` (default 60 s, from `needs_refresh_with_buffer`), call `refresh_session()`, persist the new session, emit a `TOKEN_REFRESHED` event. Retries with backoff on `Network` errors; on terminal refresh failure (revoked/invalid token) it clears state and emits `SIGNED_OUT`.

**Rationale**: FR-006 requires background refresh; the crate's own background mechanism is an unimplemented TODO, so relying on it would silently violate SC-004. The crate's manual `refresh_session()` + expiry helpers are sufficient building blocks.

**Concurrency (edge case: sign-out racing a refresh)**: all session mutations (sign-in, sign-out, refresh, restore) are serialized through a single `tokio::sync::Mutex<AuthState>` owned by the plugin's managed state. The refresh task re-checks state after acquiring the lock, so a completed sign-out can never be resurrected by an in-flight refresh. This is the single-writer design that guarantees "fully signed in or fully signed out, never a mixture".

## R4. Session persistence: OS keychain via `keyring` crate (default), pluggable

**Decision**: Persist the serialized `Session` in the OS credential store using the `keyring` crate v3 (macOS Keychain, Windows Credential Manager, Linux Secret Service). Configurable `sessionPersistence: "keychain" | "file" | "none"` (default `"keychain"`); `"file"` writes to the app's private data dir (`0600` permissions) for environments without a secret service (headless Linux/CI); `"none"` disables persistence. Corrupted/undeserializable/expired-and-unrefreshable stored sessions are treated as absent (signed-out), never a crash (FR-007). Sign-out deletes the stored entry.

**Rationale**: Keychain gives per-user, OS-protected storage with no master-password UX — the community-standard choice for desktop auth tokens. Alternatives: `tauri-plugin-store` (plain-text JSON — fails FR-007's spirit for tokens), `tauri-plugin-stronghold` (needs a user password concept; upstream in maintenance mode). supabase-lib-rs's own `EncryptedStorage`/`FileSystemStorage` backends were considered but rejected: owning persistence in the plugin keeps FR-007 guarantees independent of the dormant crate.

## R5. Plugin packaging: standard Tauri v2 plugin conventions

**Decision**: Scaffold with `npx @tauri-apps/cli plugin new supabase-auth` conventions: Rust crate **`tauri-plugin-supabase-auth`** (`src/lib.rs`, `commands.rs`, `desktop.rs`, `error.rs`, `models.rs`), `build.rs` declaring the `COMMANDS` list (auto-generates `allow-*`/`deny-*` permissions), hand-written `permissions/default.toml` defining the safe default set, and a TypeScript binding package **`guest-js/`** published as `@corpora/plugin-supabase-auth` (invoke via `invoke('plugin:supabase-auth|<command>')`, events via `listen`). Desktop-only for v1 (no `android/`/`ios/` dirs), matching the spec assumption.

**Permission model (FR-013)**: one generated permission per command; `default` set includes the session-lifecycle commands a typical app needs (`sign_in_with_password`, `sign_up`, `sign_out`, `get_session`, `get_user`, OTP + OAuth flows); mutation commands `update_user` and `reset_password_for_email` are generated but **excluded from `default`**, so developers opt in explicitly in their capabilities file.

**Configuration (FR-012)**: plugin config in `tauri.conf.json` under `plugins.supabase-auth` (`url`, `publishableKey`, `sessionPersistence`, `autoRefresh`, `oauth.callbackPorts`), deserialized and validated in the plugin `setup` hook — malformed/missing config aborts app startup with an actionable message, not at first sign-in.

## R6. UI kit: coss ui via the shadcn CLI registry, blocks as composed React components

**Decision**: The `ui/` folder is a React + Tailwind CSS v4 kit built on **coss ui** (Base UI-based, shadcn-compatible). Primitives are installed from the coss registry (`npx shadcn@latest add @coss/<component>`; registry `https://coss.com/ui/r/{name}.json`) into `ui/src/components/ui/`. Blocks (`sign-in-form`, `sign-up-form`, `forgot-password-form`, `update-password-form`, `otp-form`, `social-buttons`) live in `ui/src/blocks/` and compose `Card + Form + Field/FieldLabel/FieldError + Input + Button + Separator + OTPField + Alert + Spinner`. Client-side validation uses **zod** through the coss `Form`/`Field` pattern (Base UI Field under the hood) — field-level errors before any network call (FR-015). A `ui/src/hooks/` layer (`useAuth`, `useSession`) bridges blocks to the guest-js bindings and subscribes to auth-change events (FR-004), so blocks need only configuration-level wiring.

**Rationale**: coss ui matches the feature description, ships every needed primitive (including `OTPField` for one-time codes and `Field`-integrated validation/labeling for FR-016 accessibility), and its "particles" (`p-card-2`/`p-card-3` auth cards, `p-button-38` social login, `p-form-2` zod form) provide vetted starting points for the blocks.

**Alternatives considered**: shadcn/ui directly (Radix-based — spec directs coss); hand-rolled components (fails the "coherent, accessible" bar without far more a11y work).

## R7. Testing strategy

**Decision**:
- **Rust unit + contract tests**: `cargo test` with `wiremock` mocking the GoTrue REST surface — covers command logic, error-category mapping, PKCE exchange, refresh/race behavior, corrupted-session handling, config validation. Keyring is faked behind the persistence trait in tests.
- **UI tests**: Vitest + React Testing Library for block states (loading/success/failure, field validation) with a mocked `invoke`; `vitest-axe` for automated accessibility checks (SC-005).
- **Integration/E2E (SC-006)**: the example app plus a scripted lifecycle test (register → sign in → restart-restore → reset password → sign out) against a disposable Supabase project (`supabase start` local stack in CI), exercising the real plugin end to end.

**Rationale**: GoTrue's REST surface is small and stable, so wiremock contract tests are cheap and deterministic; the local Supabase stack in CI makes the full-lifecycle test (SC-006) reproducible without shared cloud state.
