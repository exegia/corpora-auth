# Contract: Passkey API

**Branch**: `004-passkey-auth` | **Date**: 2026-07-21

Commands, ceremony trait, event, bindings, blocks, permissions. Wire shapes per [research.md](../research.md); models per [data-model.md](../data-model.md).

## Plugin commands

All passkey commands are **opt-in** permissions (excluded from `supabase-auth:default`), registered in `build.rs` `COMMANDS` for autogenerated permissions.

### One-shot (Rust ceremony provider)

| Command | Args | Returns | Notes |
|---|---|---|---|
| `get_passkey_capability` | — | `PasskeyCapability` | Never errors; never touches the network (R7) |
| `register_passkey` | — | `{status: "completed", passkey} \| {status: "cancelled"}` | Requires signed-in non-anonymous session; options → ceremony `create` → verify; emits `PASSKEYS_CHANGED` on completed |
| `sign_in_with_passkey` | — | `{status: "completed", session} \| {status: "cancelled"}` | Signed-out entry point; options → ceremony `get` → verify → session adoption → `SIGNED_IN`; session sanitized at the boundary |
| `list_passkeys` | — | `Passkey[]` | Bearer-authenticated `GET /passkeys` |
| `rename_passkey` | `{ passkeyId, friendlyName }` | `Passkey` | Client-validates 1–120 chars before the call; emits `PASSKEYS_CHANGED` |
| `delete_passkey` | `{ passkeyId }` | `null` | 204 on server; emits `PASSKEYS_CHANGED`; **no server-side last-passkey guardrail** (R4) — confirmation UX is the kit's job |

Errors: kinds per data-model.md. `PasskeyUnsupported` is returned by `register_passkey`/`sign_in_with_passkey` when no ceremony is available (capability should have been checked first — FR-008). Ceremony wait time is outside the network timeout budget: each REST call keeps the existing `with_timeout`, but no timer spans the OS prompt (FR-014); the server's 5-minute challenge TTL is the effective ceiling, surfacing as `passkeyChallengeExpired`.

### Two-step (JS-supplied ceremony — US4 escape hatch)

| Command | Args | Returns |
|---|---|---|
| `passkey_registration_options` | — | `{ challengeId, options, expiresAt }` |
| `passkey_registration_verify` | `{ challengeId, credential }` | `Passkey` (emits `PASSKEYS_CHANGED`) |
| `passkey_authentication_options` | — | `{ challengeId, options, expiresAt }` |
| `passkey_authentication_verify` | `{ challengeId, credential }` | sanitized session (adoption + `SIGNED_IN`, same path as one-shot) |

`options` and `credential` are opaque JSON pass-throughs (R1). Both surfaces share one engine implementation per round-trip.

## Ceremony provider (Rust trait)

```rust
pub trait CeremonyProvider: Send + Sync {
    fn availability(&self) -> Availability;               // Available | Unavailable(reason)
    fn create(&self, options: &str) -> CeremonyOutcome;    // registration prompt (blocking ok; runs off the main thread)
    fn get(&self, options: &str) -> CeremonyOutcome;       // authentication prompt
}
// CeremonyOutcome: Completed(String /* credential JSON */) | Cancelled | Unsupported(String)
```

Registration: `Builder::ceremony_provider(impl CeremonyProvider + 'static)`. Precedence: app-supplied > built-in (macOS/Windows, Phase 2) > none (`Unavailable`). Built-ins take the asserted origin from plugin config `passkeys.origin` (must be listed in the project's `GOTRUE_WEBAUTHN_RP_ORIGINS` — R8).

## Event

`AuthChangeEvent::PasskeysChanged` → wire `"PASSKEYS_CHANGED"`, payload `{ event, session }` (sanitized). Emitted after successful register/rename/delete (both command surfaces). Sign-in emits `SIGNED_IN` only.

```ts
getPasskeyCapability(): Promise<PasskeyCapability>

passkeyRegistrationOptions(): Promise<PasskeyChallenge>

```

`types.ts` additions: `Passkey`, `PasskeyCapability`, `PasskeyChallenge`, result types, `AuthErrorKind` += `"passkeyChallengeExpired" | "passkeyVerificationFailed" | "passkeyUnsupported"`.

## UI kit

**`usePasskeys()`** (`ui/src/hooks/use-passkeys.ts`): `{ capability, passkeys, loading, error, refresh, register, rename, remove }` — lists on mount when signed in, refreshes on `PASSKEYS_CHANGED`, exposes cancellation as a non-error result.

**`<PasskeySignIn />`** (`ui/src/blocks/passkey-sign-in.tsx`): renders **nothing** when `capability.usable` is false (FR-012, SC-004); on click runs `signInWithPasskey`; cancelled → silent return to idle; errors → `AuthErrorAlert` with kind-specific messaging and a path back to other methods.

**`<PasskeyManager />`** (`ui/src/blocks/passkey-manager.tsx`): list (name, created, last-used), inline rename (1–120 chars, field-level validation), delete with confirmation dialog — warning copy when deleting the last passkey (kit-side only; the server does not prevent it). Add-passkey button runs `registerPasskey` then focuses the new row's rename affordance (R3: name is server-derived; rename is the customization path).

Error-message overrides extend `ErrorMessageOverrides` with the three new kinds.

## Permissions

`build.rs` `COMMANDS` += the ten commands above → autogenerated `allow-*`/`deny-*` permission pairs. `permissions/default.toml` unchanged (all passkey commands opt-in). Example app's `capabilities/default.json` lists them explicitly; docs call out the split (sign-in surface vs. management surface can be granted independently).
